# UC-03 接取救助任务

## 1. 基本信息

| 项目 | 内容 |
|---|---|
| 用例编号 | UC-03 |
| 用例名称 | 接取救助任务 |
| 主要参与者 | 救助人员 `RESCUER` |
| 用例目标 | `RESCUER` 接取一条仍处于可接取状态的救助线索，并成为对应救助任务的负责人 |
| 触发条件 | `RESCUER` 在目标线索详情页点击“接取” |
| 前置条件 | 1. `RESCUER` 已登录且账号状态正常；2. 当前角色为 `RESCUER`；3. 目标 `RescueClue` 存在；4. 目标线索当前应处于 `WAITING_ACCEPT` |
| 成功后置条件 | `RescueClue` 从 `WAITING_ACCEPT` 变为 `CONVERTED`；创建一条状态为 `WAITING_START` 的 `RescueTask`；`rescuer_id` 为当前 `RESCUER`；写入本次接取操作日志 |
| 失败后置条件 | 本次事务不提交新的 `RescueTask` 记录，不新增本次接取操作日志；系统保留数据库中最新已提交的线索和任务数据，并返回最新业务结果 |
| 优先级 | Must |

只有 `WAITING_ACCEPT` 状态的线索可以被接取。同一时刻，一条线索最多只能存在一个当前有效救助任务。

本规约中的“当前有效救助任务”是指状态为：

```text
WAITING_START
IN_PROGRESS
```

的 `RescueTask`。`SUCCESS / FAILED / CANCELED` 均为历史终态任务。

## 2. 主事件流

1. `RESCUER` 在目标救助线索详情页点击“接取”。
2. 系统后端校验当前登录状态、`RESCUER` 角色权限和目标线索标识。
3. 系统开启数据库事务。
4. 系统执行带原状态条件的更新：

```sql
UPDATE rescue_clue
SET status = 'CONVERTED',
    updated_at = NOW()
WHERE id = ?
  AND status = 'WAITING_ACCEPT';
```

5. 系统检查受影响行数：

   - `affectedRows = 1`：当前请求取得接取资格，继续执行；
   - `affectedRows = 0`：回滚事务并重新查询目标线索：
     - 查询不到：转入 E3；
     - 查询得到但状态已不是 `WAITING_ACCEPT`：转入 E4。

6. 系统创建 `RescueTask`：

```text
clue_id    = 当前 RescueClue.id
rescuer_id = 当前 RESCUER.id
status     = WAITING_START
created_at = 当前时间
updated_at = 当前时间
```

7. 系统写入接取操作对应的 `operation_log`。
8. 系统提交数据库事务。
9. 系统提示 `RESCUER`“接取成功”。
10. 新任务进入当前 `RESCUER` 的救助任务范围。
11. 用例结束。

事务结构为：

```text
条件更新 RescueClue
→ 创建 RescueTask
→ 写入 OperationLog
→ COMMIT
```

创建任务或写入日志失败时必须整体回滚。

## 3. 备选事件流

UC-03 不设置备选事件流。“浏览待接取线索”和“查看线索详情”属于前置关联功能；用户未执行接取操作时，UC-03 尚未被触发。

## 4. 异常事件流

| 编号 | 异常情况 | 系统处理 |
|---|---|---|
| E1 | 未登录或 JWT 已失效 | 拒绝接取，要求重新登录 |
| E2 | 当前账号不是 `RESCUER` | 后端拒绝请求，不修改业务数据 |
| E3 | 目标 `RescueClue` 不存在或已删除 | 回滚事务并提示线索不存在 |
| E4 | 条件更新影响 0 行，重新查询后发现状态已不是 `WAITING_ACCEPT` | 返回数据库中的最新状态，提示线索已不可接取 |
| E5 | 创建 `RescueTask` 失败 | 回滚整个事务，线索状态不提交为 `CONVERTED` |
| E6 | 写入 `operation_log` 失败 | 回滚整个事务，不产生缺少关键审计记录的接取结果 |
| E7 | 数据库事务提交失败 | 本次接取整体失败，不产生半完成业务数据 |
| E8 | `RESCUER` 重复提交同一次接取请求 | 第一次成功后状态已变为 `CONVERTED`；后续请求无法满足条件更新，按照 E3/E4 判定流程处理 |

## 5. 事务与并发控制

核心事务为：

```text
BEGIN
  ↓
条件更新 RescueClue
WAITING_ACCEPT → CONVERTED
  ↓
affectedRows = 1
  ↓
创建 RescueTask
status = WAITING_START
  ↓
写入 OperationLog
  ↓
COMMIT
```

任何一步失败均执行 `ROLLBACK`，不得出现：

```text
RescueClue = CONVERTED
但 RescueTask 不存在
```

否则线索将无法再次被接取，同时又没有对应负责人。

### 5.1 两个 RESCUER 并发接取

典型执行顺序为：

```text
RESCUER A                    RESCUER B
    │                            │
    │ 条件 UPDATE                │
    │ affectedRows = 1           │
    │                            │ 条件 UPDATE
    │                            │ 等待 A 持有的行锁
    │                            │
    │ 创建 RescueTask            │
    │ 写入 OperationLog           │
    │ COMMIT                     │
    │                            │
    │                            │ 继续执行 UPDATE
    │                            │ affectedRows = 0
    │                            │ 查询最新状态 CONVERTED
    │                            │ 接取失败
```

如果 A 在提交前执行 `ROLLBACK`，B 被唤醒后仍可能发现线索状态为 `WAITING_ACCEPT`，此时 B 的条件更新可以成功。

该并发行为以项目冻结的 MySQL 8.0 数据库及支持事务和行级锁的 InnoDB 存储引擎为实现前提。真正依赖的是：

> 数据库事务 + 条件更新 + 行锁行为

而不是用户点击按钮的先后速度。

## 6. 状态影响

UC-03 修改 `RescueClue`：

```text
WAITING_ACCEPT
      ↓
   CONVERTED
```

同时创建：

```text
RescueTask
     ↓
WAITING_START
```

`RescueTask` 的完整冻结状态机为：

```text
WAITING_START ─────→ IN_PROGRESS ─────→ SUCCESS
     │                    ├───────────→ FAILED
     │                    └───────────→ CANCELED
     │
     └───────────────────────────────→ CANCELED
```

即：

```text
WAITING_START → CANCELED
IN_PROGRESS   → CANCELED
```

均合法，但只能由 `ADMIN` 执行取消，不属于 UC-03。接取成功不等于开始现场救助，`WAITING_START → IN_PROGRESS` 属于 UC-04。

## 7. 操作日志

UC-03 写入一条线索状态变化日志：

| 字段 | 内容 |
|---|---|
| `business_type` | `RESCUE_CLUE` |
| `business_id` | 当前线索 ID |
| `operation_type` | `ACCEPT_RESCUE` |
| `before_status` | `WAITING_ACCEPT` |
| `after_status` | `CONVERTED` |
| `operator_id` | 当前 `RESCUER` ID |
| `reason` | `null` |
| `created_at` | 当前时间 |

`ACCEPT_RESCUE` 是 PetLink V1.0 已冻结的正式操作类型枚举名称；Service 必须校验其与 `RESCUE_CLUE` 的组合合法。

V1.0 不再为 `RescueTask` 创建额外写一条任务创建日志；`RescueTask.rescuer_id` 和 `created_at` 已分别保存负责人和任务创建时间。

## 9. 涉及业务规则

| 编号 | 内容 |
|---|---|
| `BR-01` | 一条线索历史上可以存在多个 `RescueTask` |
| `BR-02` | 同一时刻最多只有一个当前有效 `RescueTask` |
| `BR-03` | 只有 `WAITING_ACCEPT` 线索可以被接取 |
| `BR-14` | 关键状态变化记录操作人和时间 |

因此：

```text
历史关系：RescueClue 1 ── N RescueTask
同时有效：RescueClue 1 ── 0..1 Active RescueTask
```

数据库设计阶段不能直接设置 `UNIQUE(clue_id)`，否则会阻止同一线索在失败并重新开放后产生新的历史任务。V1.0 通过线索状态条件更新与同一事务创建任务保证当前任务唯一。

## 10. 涉及业务实体

| 实体 | 在 UC-03 中的作用 |
|---|---|
| `User` | 作为任务负责人 `RESCUER` |
| `RescueClue` | 提供任务来源并承担接取状态门控 |
| `RescueTask` | 保存新建救助任务及负责人 |
| `OperationLog` | 保存线索接取状态变化历史 |

关键关联：

```text
RescueTask.clue_id → RescueClue.id
必填，表示任务来源线索

RescueTask.rescuer_id → User.id
必填，表示该任务负责人
```

`OperationLog` 通过 `business_type + business_id` 与业务对象建立逻辑关联，不要求设置直接外键。

## 11. RescueTask 当前确认字段

```text
id
clue_id
rescuer_id
status
created_at
updated_at
```

`rescuer_id` 已经承担任务负责人含义，因此不额外设置 `created_by`。

后续由 UC-04 继续确认：

```text
started_at
finished_at
failure_reason
```

`cancel_reason` 主要来自 `ADMIN` 异常任务处理需求。
