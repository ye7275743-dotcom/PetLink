# UC-01 发布救助线索

## 1. 基本信息

| 项目 | 内容 |
|---|---|
| 用例编号 | UC-01 |
| 用例名称 | 发布救助线索 |
| 主要参与者 | 普通用户 `USER`、救助人员 `RESCUER` |
| 用例目标 | 用户发现流浪动物后，将发现地点、时间、动物描述、现场情况、联系方式及现场图片提交至平台，形成待管理员审核的救助线索 |
| 触发条件 | `USER` 或 `RESCUER` 选择“发布救助线索” |
| 前置条件 | 1. 用户已登录；2. 账号状态正常；3. 当前角色为 `USER` 或 `RESCUER` |
| 成功后置条件 | 创建一条 `RescueClue`，状态为 `PENDING_REVIEW`；保存发布人和创建时间；至少关联 1 张有效现场图片；写入创建操作日志；线索进入管理员待审核范围 |
| 失败后置条件 | 不生成有效 `RescueClue`，不保留图片关联记录；回滚本次数据库事务，并清理本次请求产生或移动的临时文件、正式文件，不产生孤立文件 |
| 优先级 | Must |

`FR-CLUE-01～10` 已明确 `USER / RESCUER` 可以发布救助线索，线索必须包含地点、时间、动物描述、图片和联系方式，并以 `PENDING_REVIEW` 状态进入后续审核流程。

## 2. 主事件流

1. `USER` 或 `RESCUER` 进入“发布救助线索”页面。
2. 系统显示救助线索发布表单。
3. 用户填写发现地点、发现时间、动物描述和联系方式，并可补充现场情况。
4. 用户上传至少一张现场图片。
5. 系统校验图片扩展名、MIME 类型、单张大小和图片数量。
6. 校验通过后，系统将图片保存至临时存储区域。
7. 用户确认信息并提交救助线索。
8. 前端对必填字段和数据格式进行基础校验。
9. 后端重新校验用户身份、角色权限和请求参数。
10. 系统开启数据库事务。
11. 系统创建 `RescueClue`，设置 `publisher_id` 为当前用户 ID，状态为 `PENDING_REVIEW`，并记录创建时间。
12. 系统预生成正式文件相对访问路径，并保存 `RescueClueImage` 图片关联记录。
13. 系统按照文件存储规则，将本次业务所需临时图片转移至正式目录。
14. 系统写入 `operation_log`，记录业务类型、新建线索 ID、操作类型、前后状态、当前操作人 ID 和操作时间。
15. 系统提交数据库事务。
16. 系统向用户返回“救助线索发布成功，等待管理员审核”。
17. 用例结束，新线索进入管理员待审核范围。

图片规则维持冻结版本：仅允许 JPG/JPEG/PNG，单张最大 5 MB，单次业务最多 9 张，使用 UUID 文件名；服务端必须同时检查扩展名、MIME 类型和文件大小。

## 3. 备选事件流

| 编号 | 触发情况 | 系统处理 |
|---|---|---|
| A1 | 用户填写过程中主动取消发布 | 系统终止本次发布，不创建 `RescueClue`；若已经产生临时上传文件，则执行清理 |

“修改线索”和“撤回线索”不属于 UC-01，因为救助线索成功发布后 UC-01 已经结束。

## 4. 异常事件流

| 编号 | 异常情况 | 系统处理 |
|---|---|---|
| E1 | 用户未登录或 JWT 已失效 | 拒绝请求，提示重新登录，不创建业务数据 |
| E2 | 当前角色不是 `USER / RESCUER` | 后端拒绝操作，不创建业务数据 |
| E3 | 地点、时间、动物描述、联系方式等必填字段缺失或格式错误 | 拒绝提交并指出错误字段 |
| E4 | 未上传任何图片 | 拒绝提交，提示“至少上传一张现场图片”，不创建 `RescueClue` |
| E5 | 图片格式不是 JPG/JPEG/PNG | 拒绝对应文件上传 |
| E6 | 单张图片超过 5 MB | 拒绝对应文件上传并提示大小限制 |
| E7 | 单次业务图片超过 9 张 | 拒绝继续上传或拒绝提交 |
| E8 | 图片扩展名与 MIME 类型不符合要求 | 服务端拒绝对应文件 |
| E9 | 临时文件转正式文件失败 | 终止本次业务；回滚数据库事务并清理本次已经产生的临时文件和正式文件 |
| E10 | 正式文件移动完成后数据库保存或事务提交失败 | 回滚本次数据库事务，删除本次请求产生或移动的临时文件、正式文件，不保留图片关联记录或孤立文件 |
| E11 | 数据库或其他服务器内部异常 | 整体业务失败，不产生半完成业务记录；向客户端返回统一业务错误，不暴露数据库信息或服务端堆栈 |
| E12 | 用户对同一次发布请求重复提交 | 对同一个幂等提交请求，系统最多生成一条 `RescueClue` 业务记录；具体采用提交令牌、幂等键或其他机制，在接口详细设计阶段确定 |

> 数据库事务只能回滚数据库数据，不能自动回滚文件系统操作。因此 E9、E10 中的文件删除属于业务层补偿机制。

## 5. 操作日志

创建成功后新增一条操作日志：

| 字段 | 值 |
|---|---|
| `business_type` | `RESCUE_CLUE` |
| `business_id` | 新建 `RescueClue.id` |
| `operation_type` | `CREATE` |
| `before_status` | `null` |
| `after_status` | `PENDING_REVIEW` |
| `operator_id` | 当前 `USER / RESCUER` ID |
| `reason` | `null` |
| `created_at` | 当前时间 |

`operation_log` 是 V1.0 核心审计实体，用于保存业务类型、业务 ID、操作类型、前后状态、操作人、原因和时间。

## 8. 涉及业务实体

```text
User 1 ───── N RescueClue

RescueClue 1 ───── 1..N RescueClueImage

RescueClue 1 ───── N OperationLog
```

| 实体 | 在 UC-01 中的作用 |
|---|---|
| `User` | 救助线索发布人 |
| `RescueClue` | 保存救助线索主体信息 |
| `RescueClueImage` | 保存线索现场图片关联 |
| `OperationLog` | 保存线索创建及后续关键状态操作历史 |

`RescueClue` 与 `OperationLog` 通过 `business_type + business_id` 建立逻辑关联，数据库设计阶段不一定设置直接外键。

### 8.1 RescueClue 候选字段

```text
id
publisher_id
location
found_time
animal_description
scene_description
contact
status
created_at
updated_at
```

这些字段是从当前用例推导出的候选字段，最终类型、长度、索引、外键、状态约束和逻辑删除字段等在数据字典阶段统一确定。

其中：

- `animal_description`：必填，用于描述动物的种类、外观、数量及可见状态等；
- `scene_description`：可选，用于补充现场环境、危险情况或其他救助信息。

## 9. 状态影响

UC-01 只负责初始化：

```text
创建 RescueClue
       ↓
PENDING_REVIEW
```

后续状态：

```text
PENDING_REVIEW
├─ REJECTED       ← UC-02 管理员驳回
├─ WAITING_ACCEPT ← UC-02 管理员审核通过
└─ WITHDRAWN      ← 发布人后续撤回
```

审核属于 UC-02，不进入 UC-01 主事件流。
