# UC-04 更新并完成救助任务

## 1. 基本信息

| 项目 | 内容 |
|---|---|
| 用例编号 | UC-04 |
| 用例名称 | 更新并完成救助任务 |
| 主要参与者 | 救助人员 `RESCUER` |
| 用例目标 | 任务负责人在救助任务生命周期内开始救助、记录救助过程，并最终以成功或失败结束任务；成功时同时建立一个或多个动物档案并关闭对应救助线索 |
| 触发条件 | 负责该任务的 `RESCUER` 在任务详情页执行“开始救助”“添加救助记录”“完成救助”或“救助失败”操作 |
| 前置条件 | `RESCUER` 已登录且账号正常；当前角色为 `RESCUER`；目标 `RescueTask` 存在；当前用户是任务负责人；任务状态满足当前操作要求 |
| 失败后置条件 | 当前这一次操作的数据库事务不提交，不新增本次操作日志；系统保留数据库中最新已提交状态。若当前操作包含图片，则清理本次请求产生或移动的临时文件及正式文件，不形成孤立文件 |
| 优先级 | Must |

### 1.1 各子流程成功后置条件

| 子流程 | 成功后置条件 |
|---|---|
| S1 开始救助 | `RescueTask: WAITING_START → IN_PROGRESS`，记录开始时间 |
| S2 添加记录 | 新增 1 条 `RescueRecord`，`RescueTask` 状态保持 `IN_PROGRESS` |
| S3 成功完成 | `RescueTask → SUCCESS`；创建 `Animal ≥ 1`；`RescueClue → CLOSED` |
| A1 救助失败 | `RescueTask → FAILED`，保存失败原因；`RescueClue` 保持 `CONVERTED` |

## 2. 用例执行说明

UC-04 是跨时间执行的复合业务用例，不是一次 HTTP 请求，也不存在覆盖整个 UC-04 的长数据库事务。它由四种独立操作组成：

```text
S1  开始救助
S2  添加救助记录      ← 可重复执行
S3  成功完成救助
A1  救助失败
```

每一次操作都独立执行：

```text
重新鉴权
→ 检查任务负责人
→ 开启数据库事务
→ 执行业务
→ COMMIT / ROLLBACK
```

## 3. S1 开始救助

1. `RESCUER` 在本人负责的任务详情页点击“开始救助”。
2. 系统校验登录身份、`RESCUER` 权限和目标任务 ID。
3. 系统开启数据库事务。
4. 系统执行条件更新：

```sql
UPDATE rescue_task
SET status = 'IN_PROGRESS',
    started_at = NOW(),
    updated_at = NOW()
WHERE id = ?
  AND rescuer_id = ?
  AND status = 'WAITING_START';
```

5. 系统检查 `affectedRows`：

   - `affectedRows = 1`：继续执行；
   - `affectedRows = 0`：回滚事务并按照统一异常分类规则处理。

6. 系统写入 `START_RESCUE` 状态变化日志。
7. 系统提交事务。
8. 返回“救助任务已开始”。

状态转换为：

```text
WAITING_START → IN_PROGRESS
```

## 4. S2 添加救助记录

该子流程可以在任务处于 `IN_PROGRESS` 时重复执行多次。

1. `RESCUER` 在任务详情页填写本次救助过程记录并提交。
2. 系统重新校验登录状态和 `RESCUER` 权限。
3. 系统开启数据库事务。
4. 系统锁定目标任务：

```sql
SELECT id, rescuer_id, status
FROM rescue_task
WHERE id = ?
FOR UPDATE;
```

5. 系统检查：

   - 记录不存在：转入 E3；
   - `rescuer_id` 不是当前用户：转入 E4；
   - `status = CANCELED`：转入 E6；
   - `status != IN_PROGRESS`：转入 E5。

6. 校验通过后创建一条 `RescueRecord`。
7. 保存任务 ID、记录内容、记录人和记录时间。
8. 系统提交事务。
9. 返回“救助记录添加成功”。

锁定任务后，状态检查与 `RescueRecord` 插入属于同一事务，从而避免任务被 ADMIN 取消后仍新增过程记录。

## 5. S3 成功完成救助

1. `RESCUER` 在任务详情页选择“完成救助”。
2. 系统要求至少填写 1 个 `Animal` 的档案信息。
3. `RESCUER` 填写一个或多个动物的信息，包括名称、种类、性别、年龄估计、毛色和健康情况等。
4. `RESCUER` 可以上传动物图片，并可填写初始健康记录。
5. 系统校验：

   - 动物数量至少为 1；
   - 动物必填字段合法；
   - 图片类型、大小和数量符合规则；
   - 本次完成救助提交中的所有 Animal 图片合计最多 9 张。

6. 图片通过独立的已鉴权上传请求进入临时存储区域。
7. 系统在提交完成请求时重新校验当前用户身份与 `RESCUER` 权限。
8. 系统开启数据库事务。
9. 系统执行任务条件更新：

```sql
UPDATE rescue_task
SET status = 'SUCCESS',
    finished_at = NOW(),
    updated_at = NOW()
WHERE id = ?
  AND rescuer_id = ?
  AND status = 'IN_PROGRESS';
```

10. 系统检查受影响行数：

    - `affectedRows = 1`：继续执行；
    - `affectedRows = 0`：回滚事务并按照统一异常分类规则处理。

11. 任务条件更新成功后，系统在当前事务内从 `RescueTask` 记录读取 `clue_id`。

    `RescueTask.clue_id` 是本次关闭救助线索的唯一依据。客户端不得指定或覆盖关联线索 ID，只需提交目标 `task_id`。

12. 系统创建一个或多个 `Animal`：

```text
Animal.rescue_task_id = 当前 RescueTask.id
Animal.status = TREATING
```

13. 系统创建对应的 `AnimalImage`。
14. 如填写了初始健康记录，系统为对应动物创建 `HealthRecord`：

```text
animal_id   = 当前新建 Animal.id
recorder_id = 当前 RESCUER.id
recorded_at = 当前时间
```

15. 系统将本次临时图片移动到正式目录，并保存相对访问路径。
16. 系统根据由当前任务读取的 `clue_id` 条件更新原救助线索：

```sql
UPDATE rescue_clue
SET status = 'CLOSED',
    updated_at = NOW()
WHERE id = ?
  AND status = 'CONVERTED';
```

17. 系统检查线索更新影响行数：

    - `affectedRows = 1`：继续执行；
    - 其他结果：整体回滚 S3 数据库事务，并执行图片文件补偿清理。

18. 系统写入 `COMPLETE_RESCUE` 和 `CLOSE_AFTER_RESCUE` 两条操作日志。
19. 系统提交数据库事务。
20. 返回“救助任务完成”。

虽然代码执行顺序中先将任务更新为 `SUCCESS`，但该状态在提交前不是最终业务结果。Animal 创建、线索关闭、日志写入或事务提交任一步失败时均执行 `ROLLBACK`，任务状态也会恢复，因此仍严格满足 `BR-26`。

## 6. A1 救助失败

1. `RESCUER` 选择“救助失败”。
2. 系统要求填写失败原因。
3. `RESCUER` 输入失败原因并提交。
4. 系统校验失败原因不为空且不只包含空白字符。
5. 系统重新校验登录身份和 `RESCUER` 权限。
6. 系统开启数据库事务。
7. 系统执行条件更新：

```sql
UPDATE rescue_task
SET status = 'FAILED',
    failure_reason = ?,
    finished_at = NOW(),
    updated_at = NOW()
WHERE id = ?
  AND rescuer_id = ?
  AND status = 'IN_PROGRESS';
```

8. 系统检查受影响行数：

   - `affectedRows = 1`：继续执行；
   - `affectedRows = 0`：回滚事务并按照统一异常分类规则处理。

9. 系统写入 `RESCUE_FAILED` 操作日志。
10. 系统提交事务。
11. 返回“救助任务已标记失败”。

此时：

```text
RescueTask = FAILED
RescueClue = CONVERTED
```

线索不自动重新开放，也不自动关闭。后续由 `ADMIN` 决定执行：

```text
CONVERTED → WAITING_ACCEPT
```

或：

```text
CONVERTED → CLOSED
```

## 7. 统一异常事件流

S1、S3、A1 的条件更新影响 0 行时，统一回滚并重新查询 `RescueTask`，然后分类处理：

| 编号 | 情况 | 系统处理 |
|---|---|---|
| E1 | JWT 失效或未登录 | 拒绝请求并要求重新登录 |
| E2 | 当前角色不是 `RESCUER` | 后端拒绝操作 |
| E3 | `RescueTask` 不存在或已删除 | 返回“任务不存在或已删除” |
| E4 | `rescuer_id` 不是当前用户 | 拒绝操作，提示无权修改该任务 |
| E5 | 当前状态不满足当前操作要求 | 返回数据库中的最新状态，拒绝非法转换 |
| E6 | 当前状态为 `CANCELED` | 返回“任务已由管理员取消”，不得继续记录或完成 |
| E7 | `FAILED` 时失败原因为空或仅包含空白字符 | 拒绝失败提交 |
| E8 | `SUCCESS` 时没有提供任何 Animal | 拒绝完成 |
| E9 | Animal 必填数据不完整 | 拒绝完成 |
| E10 | Animal、Image 或 HealthRecord 创建失败 | 成功完成事务整体回滚 |
| E11 | 关闭 `RescueClue` 影响行数不是 1 | 整体回滚 |
| E12 | 任一必需 `OperationLog` 写入失败 | 整体回滚 |
| E13 | 数据库提交失败 | 当前操作整体失败 |
| E14 | 正式文件移动失败或数据库事务失败 | 回滚数据库；业务层删除本次临时文件及已经移动的正式文件 |
| E15 | 重复点击“完成救助” | 第一次成功后任务不再是 `IN_PROGRESS`，后续请求按照 E5 返回最新状态 |

## 8. 状态影响

### 8.1 RescueTask

```text
WAITING_START ─────→ IN_PROGRESS ─────→ SUCCESS
     │                    ├───────────→ FAILED
     │                    └───────────→ CANCELED
     │
     └───────────────────────────────→ CANCELED
```

UC-04 执行：

```text
WAITING_START → IN_PROGRESS
IN_PROGRESS → SUCCESS
IN_PROGRESS → FAILED
```

两条进入 `CANCELED` 的转换只能由 `ADMIN` 执行。

### 8.2 RescueClue

- 成功：`CONVERTED → CLOSED`；
- 失败：保持 `CONVERTED`，等待 ADMIN 决策。

### 8.3 Animal

成功完成救助时创建，初始状态为 `TREATING`。后续的 `TREATING → OBSERVING → AVAILABLE` 属于动物档案维护，不进入 UC-04。

## 9. 图片规则

S3 使用统一文件规则：

- 仅允许 JPG/JPEG/PNG；
- 单张最大 5 MB；
- 一次“完成救助”提交中，所有动物图片合计最多 9 张；
- 使用 UUID 文件名；
- 采用“临时目录 → 正式目录”的文件生命周期；
- 数据库或文件移动失败时不得产生孤立图片。

数据库事务不能自动回滚文件系统，因此失败时必须由业务层执行补偿删除。

## 12. 涉及业务规则

| 编号 | 内容 |
|---|---|
| `BR-04` | 只有救助成功后才能建立正式动物档案 |
| `BR-13` | `RESCUER` 只能修改本人负责的救助任务及相关数据 |
| `BR-14` | 关键状态变化必须记录操作人与时间 |
| `BR-17` | `FAILED` 后由 `ADMIN` 决定线索去向 |
| `BR-23` | 一个成功 `RescueTask` 可以产生一个或多个 Animal，每个 Animal 只能来源于一个 RescueTask |
| `BR-26` | `SUCCESS`、至少一个 Animal、线索 `CLOSED` 必须同事务完成 |
| `BR-27` | 任务取消仅属于 `ADMIN` |

## 13. 涉及业务实体与关系

| 实体 | 在 UC-04 中的作用 |
|---|---|
| `User` | 作为任务负责人和记录人 |
| `RescueClue` | 在成功路径中由系统联动关闭 |
| `RescueTask` | 保存任务负责人、状态和开始/结束信息 |
| `RescueRecord` | 保存可重复添加的救助过程记录 |
| `Animal` | 保存成功救助后建立的动物档案 |
| `AnimalImage` | 保存动物图片关联 |
| `HealthRecord` | 保存可选的初始健康记录 |
| `OperationLog` | 保存关键状态变化历史 |

关系基数：

```text
RescueClue 1 —— 0..N RescueTask
RescueTask 1 —— 0..N RescueRecord
RescueTask 1 —— 0..N Animal
Animal 1 —— 0..N AnimalImage
Animal 1 —— 0..N HealthRecord
```

附加约束：

```text
当 RescueTask.status = SUCCESS 时，对应 Animal 数量必须 >= 1。
每个 Animal 必须且只能来源于一个 RescueTask。
```

`OperationLog` 通过 `business_type + business_id` 与业务对象建立逻辑关联，不要求设置直接外键。

## 14. RescueTask 当前确认字段

```text
id
clue_id
rescuer_id
status
started_at
finished_at
failure_reason

```

`cancel_reason` 由 ADMIN 异常取消业务填写，不由 UC-04 的 `RESCUER` 填写。

## 15. 前后业务衔接

```text
UC-03 完成后：
RescueClue = CONVERTED
RescueTask = WAITING_START

UC-04：
WAITING_START
      ↓
IN_PROGRESS
      ↓
 ┌────┴────┐
 ↓         ↓
SUCCESS   FAILED
 ↓          ↓
Animal ≥ 1  等待 ADMIN 决策
 ↓
Clue CLOSED
```

成功路径之后，Animal 仍需经过：

```text
TREATING → OBSERVING → AVAILABLE
```

只有进入 `AVAILABLE` 后，才会衔接 UC-05 提交领养申请。
