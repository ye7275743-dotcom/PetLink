# UC-06 审核领养申请

## 1. 基本信息

| 项目 | 内容 |
|---|---|
| 用例编号 | UC-06 |
| 用例名称 | 审核领养申请 |
| 主要参与者 | 系统管理员 `ADMIN` |
| 用例目标 | `ADMIN` 对待审核领养申请作出批准或拒绝决定；批准时原子完成领养记录创建、动物状态更新及其他竞争申请自动失效 |
| 触发条件 | `ADMIN` 在待审核领养申请详情页点击“批准”或“拒绝” |
| 前置条件 | 1. `ADMIN` 已登录且账号正常；2. 当前角色为 `ADMIN`；3. 目标 `AdoptionApplication` 存在；4. 目标申请当前应为 `PENDING` |
| 批准成功后置条件 | 当前申请变为 `APPROVED`；创建唯一的 `AdoptionRecord`；目标 `Animal` 从 `AVAILABLE → ADOPTED`；同一动物的其他 `PENDING` 申请变为 `INVALIDATED`；保存审核人、审核时间并写入全部关键操作日志 |
| 拒绝成功后置条件 | 当前申请从 `PENDING → REJECTED`；保存拒绝原因、审核人和审核时间；`Animal` 状态不变；写入拒绝审核日志 |
| 失败后置条件 | 本次审核事务不提交任何修改，不新增本次审核对应日志；数据库保留最新已提交数据并返回最新业务状态 |
| 优先级 | Must |

领养申请状态机为：

```text
PENDING
├─ APPROVED
├─ REJECTED
├─ WITHDRAWN
└─ INVALIDATED
```

## 2. 用例边界

UC-06 从 `ADMIN` 正式提交审核决定开始，负责：

```text
审核批准
或
审核拒绝
```

查看待审核申请、查看申请详情属于前置关联功能；申请人执行的 `PENDING → WITHDRAWN` 不属于 UC-06。

审核接口仅允许客户端提交：

```text
application_id
审核动作
reject_reason（拒绝时）
```

以下数据必须来自数据库或认证上下文，客户端不得指定或覆盖：

```text
user_id
animal_id
reviewer_id
```

`AdoptionApplication.user_id` 与 `AdoptionApplication.animal_id` 在申请创建后不得修改。

## 3. S1：审核批准

### 3.1 主事件流

1. `ADMIN` 在目标申请详情页点击“批准”。
2. 后端重新校验当前登录身份、`ADMIN` 权限、目标申请 ID 及请求参数。
3. 系统根据目标 `AdoptionApplication.id` 预读取 `animal_id`：

```sql
SELECT animal_id
FROM adoption_application
WHERE id = ?;
```

该值仅用于确定需要优先锁定的 `Animal`，不作为申请状态、申请人身份或审核资格的最终判断依据。若预读取不到申请，直接转入 E3，不开启审核事务。

4. 系统开启数据库事务。
5. 系统按照领养模块统一锁顺序，先锁定目标 `Animal`：

```sql
SELECT id, status, version
FROM animal
WHERE id = ?
FOR UPDATE;
```

6. 系统检查：

   - `Animal` 不存在或已删除：回滚并转入 E4；
   - `status != AVAILABLE`：回滚并转入 E5；
   - `status = AVAILABLE`：继续执行。

7. 系统锁定目标 `AdoptionApplication`：

```sql
SELECT id, user_id, animal_id, status
FROM adoption_application
WHERE id = ?
FOR UPDATE;
```

8. 系统基于锁定后的最新记录重新检查：

   - 申请不存在或已删除：回滚并转入 E3；
   - `animal_id` 与已锁定的 `Animal.id` 不一致：回滚并返回数据一致性异常；
   - `user_id = 当前 ADMIN.id`：回滚并转入 E7；
   - `status != PENDING`：回滚并转入 E6；
   - 全部校验通过：继续执行。

9. 系统更新当前申请：

```sql
UPDATE adoption_application
SET status = 'APPROVED',
    reviewer_id = ?,
    reviewed_at = NOW(),
    reject_reason = NULL,
    updated_at = NOW()
WHERE id = ?
  AND status = 'PENDING';
```

10. 系统检查受影响行数：

```text
affectedRows = 1
→ 继续

affectedRows = 0
→ 回滚并重新查询目标申请：
   · 查询不到 → E3
   · 查询得到但状态不再是 PENDING → E6
```

11. 系统创建 `AdoptionRecord`：

```text
application_id = 当前申请 ID
animal_id      = 已锁定的 Animal.id
user_id        = 已锁定申请的 user_id
adopted_at     = 当前时间
created_at     = 当前时间
```

12. 系统更新目标动物：

```sql
UPDATE animal
SET status = 'ADOPTED',
    version = version + 1,
    updated_at = NOW()
WHERE id = ?
  AND status = 'AVAILABLE'
  AND version = ?;
```

`version` 使用第 5 步锁定 Animal 后读取的最新值。即使行锁已经提供事务级互斥，批准事务仍递增乐观锁版本，保持所有 Animal 写操作的版本语义一致。

13. 若 `affectedRows != 1`，整个批准事务回滚。
14. 系统按固定顺序锁定同一动物的其他待审核申请：

```sql
SELECT id
FROM adoption_application
WHERE animal_id = ?
  AND id <> ?
  AND status = 'PENDING'
ORDER BY id
FOR UPDATE;
```

15. 系统保存查询结果：

```text
invalidatedIds = [id1, id2, ...]
expectedCount  = invalidatedIds.size()
```

16. 系统批量更新其他申请：

```sql
UPDATE adoption_application
SET status = 'INVALIDATED',
    updated_at = NOW()
WHERE animal_id = ?
  AND id <> ?
  AND status = 'PENDING';
```

17. 系统核对更新数量：

```text
affectedRows == expectedCount
→ 继续

affectedRows != expectedCount
→ 整体回滚
```

当 `expectedCount = 0` 且 `affectedRows = 0` 时属于正常情况。

18. 系统写入当前申请的批准日志。
19. 系统写入 `Animal: AVAILABLE → ADOPTED` 状态变化日志。
20. 系统对 `invalidatedIds` 中的每条申请分别写入 `AUTO_INVALIDATE` 日志。
21. 系统提交事务。
22. 系统返回“领养申请审核通过”。
23. 用例结束。

### 3.2 批准事务原子性

批准操作必须在同一事务内完成：

```text
预读取 application.animal_id（仅用于锁路由）
        ↓
BEGIN
        ↓
锁 Animal 并确认 AVAILABLE
        ↓
锁目标 AdoptionApplication
        ↓
重新确认 animal_id、user_id、status
        ↓
当前申请 → APPROVED
        ↓
创建 AdoptionRecord
        ↓
Animal → ADOPTED
        ↓
锁定其他 PENDING 申请集合
        ↓
批量 → INVALIDATED 并核对数量
        ↓
写入全部关键 OperationLog
        ↓
COMMIT
```

任何一步失败均必须 `ROLLBACK`，不允许出现以下中间结果：

```text
Application 已 APPROVED，但 AdoptionRecord 不存在
AdoptionRecord 已生成，但 Animal 仍为 AVAILABLE
Animal 已 ADOPTED，但其他 PENDING 申请仍等待审核
关键状态已经变化，但对应 OperationLog 缺失
```

## 4. A1：审核拒绝

拒绝路径只修改 `AdoptionApplication`，不锁定也不修改 `Animal`。

1. `ADMIN` 点击“拒绝”。
2. 系统要求填写拒绝原因。
3. `ADMIN` 输入原因并提交。
4. 后端校验：

   - 当前登录身份有效；
   - 当前角色为 `ADMIN`；
   - 目标申请 ID 合法；
   - 拒绝原因不为空且不只包含空白字符；
   - 拒绝原因长度合法；
   - `reviewer_id` 只能取自认证上下文。

5. 系统开启数据库事务。
6. 系统锁定目标 `AdoptionApplication`：

```sql
SELECT id, user_id, animal_id, status
FROM adoption_application
WHERE id = ?
FOR UPDATE;
```

7. 系统检查：

   - 申请不存在或已删除：回滚并转入 E3；
   - `user_id = 当前 ADMIN.id`：回滚并转入 E7；
   - `status != PENDING`：回滚并转入 E6；
   - 全部校验通过：继续执行。

8. 系统执行：

```sql
UPDATE adoption_application
SET status = 'REJECTED',
    reviewer_id = ?,
    reviewed_at = NOW(),
    reject_reason = ?,
    updated_at = NOW()
WHERE id = ?
  AND status = 'PENDING';
```

9. 系统检查受影响行数：

```text
affectedRows = 1
→ 继续

affectedRows = 0
→ 回滚并重新查询目标申请，按 E3 / E6 分类
```

10. 系统写入 `AUDIT_REJECT` 操作日志。
11. 系统提交事务。
12. 系统返回“领养申请已拒绝”。
13. 用例结束。

拒绝结果为：

```text
AdoptionApplication: PENDING → REJECTED
Animal: 状态不变
```

由于 `UNIQUE(user_id, animal_id)` 继续保留，该申请人不能针对同一动物重新提交申请。

## 5. 并发与加锁规则

PetLink 领养模块统一采用以下规则：

> 当同一写事务同时需要操作 `Animal` 与 `AdoptionApplication` 时，统一按照 `Animal → AdoptionApplication` 的顺序加锁。仅操作 `AdoptionApplication` 的事务无需额外锁定 `Animal`。

因此：

```text
UC-05 创建申请
→ 先锁 Animal，再创建 AdoptionApplication

UC-06 批准申请
→ 先锁 Animal，再锁目标及其他 AdoptionApplication

UC-06 拒绝申请
→ 仅锁目标 AdoptionApplication
```

同一动物存在多份申请时，两个 `ADMIN` 并发批准不同申请：

```text
ADMIN A 先锁定 Animal
→ ADMIN B 等待同一 Animal 锁
→ ADMIN A 完成批准并提交，Animal 变为 ADOPTED
→ ADMIN B 获得锁后发现 Animal 不再是 AVAILABLE
→ ADMIN B 的批准事务失败
```

最终保证一只 `Animal` 最多产生一条成功的 `AdoptionRecord`。

申请人并发撤回与 `ADMIN` 审核时，谁先锁定目标申请并成功完成合法状态转换，谁的结果生效；后续事务必须读取最新状态，不能依赖页面中的旧状态。

## 6. 异常事件流

| 编号 | 异常情况 | 系统处理 |
|---|---|---|
| E1 | `ADMIN` 未登录或 JWT 失效 | 拒绝审核并要求重新登录 |
| E2 | 当前用户不是 `ADMIN` | 后端拒绝请求 |
| E3 | 目标 `AdoptionApplication` 不存在或已删除 | 不开启事务或回滚事务，返回申请不存在 |
| E4 | 批准时目标 `Animal` 不存在或已删除 | 回滚批准事务 |
| E5 | 批准时 `Animal` 已不是 `AVAILABLE` | 回滚事务，返回动物最新状态；不得批准 |
| E6 | 申请当前已不是 `PENDING` | 回滚事务，返回申请最新状态 |
| E7 | 审核人与申请人为同一账户 | 拒绝审核并回滚事务，不写入本次审核日志 |
| E8 | 拒绝原因缺失、仅含空白或长度不合法 | 拒绝执行 `REJECTED` 转换 |
| E9 | 创建 `AdoptionRecord` 失败或触发唯一约束 | 整体回滚 |
| E10 | `Animal → ADOPTED` 更新影响行数不是 1 | 整体回滚 |
| E11 | 其他申请 `INVALIDATED` 的实际更新数与预期不一致 | 整体回滚 |
| E12 | 任一必需 `OperationLog` 写入失败 | 整体回滚 |
| E13 | 数据库事务提交失败 | 当前审核整体失败 |
| E14 | 两个 `ADMIN` 并发批准同一动物的不同申请 | 后进入者等待 `Animal` 锁；获得锁后发现动物已为 `ADOPTED`，批准失败 |
| E15 | 申请人在审核前并发撤回，或另一管理员并发拒绝 | 后执行者读取最新状态；若已非 `PENDING`，按 E6 处理 |
| E16 | `ADMIN` 重复点击批准或拒绝 | 第一次合法转换后申请已非 `PENDING`；后续请求按 E6 处理 |

## 7. 操作日志

### 7.1 批准申请日志

```text
business_type  = ADOPTION_APPLICATION
business_id    = 当前 Application.id
operation_type = AUDIT_APPROVE
before_status  = PENDING
after_status   = APPROVED
operator_id    = 当前 ADMIN.id
reason         = null
created_at     = 当前时间
```

### 7.2 动物领养状态日志

```text
business_type  = ANIMAL
business_id    = 当前 Animal.id
operation_type = ADOPT
before_status  = AVAILABLE
after_status   = ADOPTED
operator_id    = 当前 ADMIN.id
reason         = null
created_at     = 当前时间
```

`ADOPTED` 只能由领养批准事务自动产生。这里的 `operator_id` 表示触发事务的 `ADMIN`，不表示管理员可以脱离审核流程手工设置动物状态。

### 7.3 其他申请自动失效日志

对 `invalidatedIds` 中的每条申请必须分别记录：

```text
business_type  = ADOPTION_APPLICATION
business_id    = 当前被失效申请 ID
operation_type = AUTO_INVALIDATE
before_status  = PENDING
after_status   = INVALIDATED
operator_id    = 当前 ADMIN.id
reason         = 同动物的申请 {approvedApplicationId} 已批准
created_at     = 当前时间
```

自动失效申请仅更新 `status` 和 `updated_at`；其 `reviewer_id`、`reviewed_at`、`reject_reason` 保持为空，因为该申请没有被管理员逐条审核或驳回。自动状态变化由 `AUTO_INVALIDATE` 日志负责追溯。

### 7.4 拒绝申请日志

```text
business_type  = ADOPTION_APPLICATION
business_id    = 当前 Application.id
operation_type = AUDIT_REJECT
before_status  = PENDING
after_status   = REJECTED
operator_id    = 当前 ADMIN.id
reason         = 拒绝原因
created_at     = 当前时间
```

## 9. 涉及业务规则

| 规则编号 | 内容 |
|---|---|
| `BR-05` | 只有 `AVAILABLE` 动物可以接受领养 |
| `BR-07` | 用户不能审核自己的领养申请 |
| `BR-08` | 领养申请最终审核权仅属于 `ADMIN` |
| `BR-09` | 一只动物最多产生一条成功的 `AdoptionRecord` |
| `BR-10` | 一份申请通过后，同动物其他 `PENDING` 申请自动变为 `INVALIDATED` |
| `BR-11` | `ADOPTED` 动物不得继续接受领养申请 |
| `BR-14` | 关键审核和状态变化必须记录操作人及时间 |
| `BR-20` | `ADOPTED` 只能由领养批准事务自动触发 |
| `BR-21` | `USER / RESCUER` 均可申请，但最终审核权仅属于 `ADMIN` |
| `BR-28` | `RESCUER` 可以申请领养，但不能审核领养申请 |

## 10. 涉及业务实体与关系

UC-06 涉及：

```text
User
Animal
AdoptionApplication
AdoptionRecord
OperationLog
```

核心关系：

```text
User(USER / RESCUER) 1 ─── 0..N AdoptionApplication
Animal                1 ─── 0..N AdoptionApplication

AdoptionApplication   1 ─── 0..1 AdoptionRecord
Animal                1 ─── 0..1 AdoptionRecord
User                  1 ─── 0..N AdoptionRecord
```

`AdoptionApplication` 与 `User` 还存在审核关系：

```text
AdoptionApplication.reviewer_id → User.id
```

该外键在 `APPROVED / REJECTED` 时指向执行审核的 `ADMIN`；系统自动置为 `INVALIDATED` 时保持为空。

## 11. 字段与数据库约束

### 11.1 AdoptionApplication 审核字段

```text
reviewer_id
reviewed_at
reject_reason
```

字段语义：

```text
APPROVED
→ reviewer_id、reviewed_at 有值
→ reject_reason 为 null

REJECTED
→ reviewer_id、reviewed_at、reject_reason 均有值

INVALIDATED
→ reviewer_id、reviewed_at、reject_reason 均为空
→ 通过 OperationLog 追踪自动失效原因
```

### 11.2 AdoptionRecord 候选字段

```text
id
application_id
animal_id
user_id
adopted_at
created_at
```

其中 `application_id`、`animal_id`、`user_id` 全部从锁定后的数据库记录取得，不接受客户端覆盖。

`AdoptionRecord` 是不可变成功领养事实，不包含 `updated_at / version / deleted`。V1.0 中 ADMIN 对领养记录的管理仅指查询、查看详情、业务监管和关联追踪，不允许手工新增、修改或删除。

### 11.3 AdoptionRecord 唯一约束

```sql
CONSTRAINT uk_adoption_record_application
UNIQUE (application_id)
```

保证一个 `AdoptionApplication` 最多生成一条 `AdoptionRecord`。

```sql
CONSTRAINT uk_adoption_record_animal
UNIQUE (animal_id)
```

保证一只 `Animal` 最多生成一条成功领养记录。

`user_id` 不设置唯一约束，因为同一用户历史上可以合法领养多只动物。

## 12. 状态影响总览

批准：

```text
AdoptionApplication: PENDING → APPROVED
Animal:               AVAILABLE → ADOPTED
其他同动物申请:         PENDING → INVALIDATED
同时创建:              AdoptionRecord
```

拒绝：

```text
AdoptionApplication: PENDING → REJECTED
Animal:               状态不变
```

核心流程：

```text
                    ┌─ 拒绝 ─→ REJECTED
                    │
Application PENDING ┤
                    │
                    └─ 批准 ─→ APPROVED
                                │
                                ├─ 创建 AdoptionRecord
                                ├─ Animal → ADOPTED
                                └─ 其他 PENDING → INVALIDATED
```
