# UC-07 提交领养回访

## 1. 基本信息

| 项目 | 内容 |
|---|---|
| 用例编号 | UC-07 |
| 用例名称 | 提交领养回访 |
| 主要参与者 | 普通用户 `USER`、救助人员 `RESCUER` |
| 用例目标 | 已完成领养的 `USER / RESCUER` 针对本人领养记录提交动物后续生活及健康情况，形成新的 `FollowUpRecord` |
| 触发条件 | `USER / RESCUER` 在本人领养记录详情页点击“提交回访”，填写内容后点击“提交” |
| 前置条件 | 1. 用户已登录且账号正常；2. 当前角色为 `USER` 或 `RESCUER`；3. 目标 `AdoptionRecord` 存在；4. `AdoptionRecord.user_id` 为当前登录用户 |
| 成功后置条件 | 新增且仅新增一条 `FollowUpRecord`，正确关联目标 `AdoptionRecord`；保存提交人和提交时间；如包含图片则建立对应 `FollowUpImage` 关联；不修改 `AdoptionRecord` 和 `Animal` 状态 |
| 失败后置条件 | 本次请求不新增 `FollowUpRecord / FollowUpImage`；系统保留数据库中最新已提交数据；只删除能够确认由本事务创建的正式副本，合法原临时文件继续保留 |
| 优先级 | Must |

## 2. 用例边界

UC-07 负责：

```text
进入本人领养记录
      ↓
填写回访
      ↓
提交回访
      ↓
创建 FollowUpRecord
```

以下功能不属于 UC-07：

```text
ADMIN 查看全部回访
RESCUER 查看本人曾负责动物的回访
```

需要区分 `RESCUER` 的两种业务身份：

```text
作为领养人
→ 可以针对本人 AdoptionRecord 提交回访

作为动物原救助负责人
→ 只能查看对应回访
→ 不能因此提交、修改或删除他人的回访
```

是否具有提交权限，只根据：

```text
AdoptionRecord.user_id = 当前认证用户.id
```

判断，不根据原救助任务的 `rescuer_id` 判断。

## 3. 回访内容有效性规则

每次回访至少包含以下三项中的一项：

```text
有效文字描述
健康情况
至少一张有效生活照片
```

禁止提交完全空白的 `FollowUpRecord`。服务端应先对文字字段执行去除首尾空白处理：

```text
content.trim()
health_condition.trim()
```

只有处理后仍包含内容的字段才视为有效文字。若两个文字字段均为空，且不存在有效生活照片，则拒绝提交。

## 4. 主事件流

1. `USER / RESCUER` 在本人领养记录详情页进入回访表单并填写文字、健康情况和生活照片。
2. 客户端对图片进行基础校验并上传至临时区域，服务器为每个文件签发 `tempFileToken`。
3. 用户点击“提交回访”，前端立即禁用提交按钮。
4. 后端校验登录身份、`USER / RESCUER` 角色、目标领养记录 ID 以及文字字段格式和长度；`submitter_id` 只能来自认证上下文。
5. 后端校验客户端只提交临时文件 token，禁止提交服务器文件路径或正式存储路径。
6. 服务端校验 `idempotency_key` 为标准 UUID，并规范化为小写。
7. 服务端对文字字段执行 `trim`，将空字符串和纯空白转换为 `NULL`。
8. 系统检查 `imageTokens` 数量为 0～9、列表内部无重复，并确认文字、健康情况或图片至少存在一项表面有效内容。
9. 系统普通读取目标 `AdoptionRecord`：

```sql
SELECT id, user_id, animal_id
FROM adoption_record
WHERE id = ?;
```

10. 系统确认记录存在且 `user_id = 当前认证用户.id`。`AdoptionRecord` 不可修改或删除，因此无需 `FOR UPDATE`。
11. 系统根据 `submitter_id + idempotency_key` 查询已有结果：

    - 已存在且 `adoption_record_id` 相同：返回第一次成功结果，不处理图片；
    - 已存在但 `adoption_record_id` 不同：返回幂等键冲突；
    - 不存在：继续。

12. 系统开启数据库事务并创建 `FollowUpRecord`，首先占用幂等键：

```text
adoption_record_id = 当前 AdoptionRecord.id
submitter_id       = 当前认证用户.id
content            = 规范化后的文字（如有）
health_condition   = 规范化后的健康情况（如有）
idempotency_key    = 规范化后的小写 UUID
created_at         = 当前时间
```

13. 如发生命名唯一约束 `uk_follow_up_submitter_idempotency` 冲突，系统回滚当前事务并重新查询已有记录，按照第 11 步返回原结果或幂等键冲突。其他完整性异常不得解释为幂等重试。
14. 如包含图片，系统根据 token 批量查询 `temporary_file`，并按 `temporary_file.id ASC` 执行 `FOR UPDATE`；实际查询数量必须与请求 token 数量完全一致。
15. 系统逐项重新验证临时文件所有者、状态、有效期、扩展名、MIME、大小及物理文件。
16. 系统为每张图片生成正式 UUID 相对路径，并按客户端原始 token 顺序创建 `FollowUpImage`：

```text
follow_up_id = 新建 FollowUpRecord.id
image_path   = 后端生成的正式相对路径
sort_order   = 客户端 token 原顺序 1..N
created_at   = 当前时间
```

17. 系统对每个临时文件执行带 `owner_id / status / expires_at` 条件的绑定更新，将其置为 `BOUND` 并关联当前回访；任一 `affectedRows != 1` 时整体回滚。
18. 系统复制合法临时文件到正式路径，并记录本事务已经创建的正式副本集合。
19. 全部复制成功后提交数据库事务。
20. 提交成功后删除本次已成功绑定的原临时物理文件；删除失败只记录错误并交由清理任务处理，不回滚业务。
21. 系统返回“回访提交成功”及新建 `FollowUpRecord.id`，用例结束。

客户端不得直接提交服务器文件系统路径，也不得指定最终正式存储路径。例如以下输入均不接受：

```text
/uploads/followup/2026/08/a.jpg
C:\uploads\a.jpg
```

客户端只能提交服务端签发的临时文件标识，由后端根据临时文件记录生成最终正式相对路径。

## 5. A1：用户取消提交

1. 用户在填写过程中选择取消或返回。
2. 系统不启动 `FollowUpRecord` 创建事务。
3. 系统不创建 `FollowUpRecord` 和 `FollowUpImage`。
4. 系统不直接删除未消费的临时上传文件，由统一的过期临时文件清理任务兜底。
5. 用例结束。

## 6. 文件与数据库一致性

无图片时：

```text
校验 AdoptionRecord 所有权
  ↓
规范化并检查幂等键
  ↓
BEGIN
  ↓
创建 FollowUpRecord 并占用唯一幂等键
  ↓
COMMIT
```

有图片时：

```text
临时上传图片并取得 tempFileToken
      ↓
校验 token 数量、去重及领养记录所有权
      ↓
BEGIN
      ↓
创建 FollowUpRecord
      ↓
按 temporary_file.id 升序锁定并重新校验
      ↓
创建 0..N FollowUpImage
      ↓
条件绑定 TemporaryFile
      ↓
复制临时文件到正式目录
      ↓
COMMIT
      ↓
删除原临时物理文件
```

若数据库操作、文件复制或事务提交失败，则：

```text
ROLLBACK
+ 仅删除能够确认由本事务创建的正式副本
+ 保留合法原临时文件
```

数据库事务不能自动回滚文件系统操作，因此提交前采用复制而不是移动。数据库提交成功但删除原临时文件失败时，不回滚正式业务，只记录错误并由定时清理机制兜底。补偿逻辑只能处理已经验证属于当前用户并能够确认由本事务创建、复制或绑定的文件，不得删除其他用户、其他业务或客户端伪造路径对应的文件。

## 7. 多次回访与幂等控制

一次成功领养允许主动提交多次回访：

```text
AdoptionRecord #1001
├── 9 月 1 日  → FollowUpRecord #1
├── 10 月 1 日 → FollowUpRecord #2
└── 11 月 1 日 → FollowUpRecord #3
```

因此不得设置：

```sql
UNIQUE (adoption_record_id)
```

否则会把 `1:N` 错误限制为 `1:1`。

但同一次请求因重复点击或网络重试被再次执行时，不得创建重复记录。系统采用以下措施：

```text
前端提交后立即禁用按钮
+ 后端使用持久化幂等键识别同一请求
+ 重复请求返回第一次请求的业务结果
```

`idempotency_key` 使用客户端生成的标准 UUID，服务端校验并规范化为小写；随 `FollowUpRecord` 永久保存，创建后不可修改、释放或过期。同一用户的新回访必须生成新的幂等键。

数据库通过命名唯一约束 `uk_follow_up_submitter_idempotency(submitter_id, idempotency_key)` 最终防重。只有该约束冲突可解释为幂等重试。若已有记录属于相同领养记录，则返回第一次结果；属于不同领养记录则返回冲突。V1.0 不保存请求哈希，同一 key、同一领养记录重试时始终以第一次成功提交为准。

## 8. 状态影响

UC-07 仅新增历史回访数据，不产生新的状态转换：

```text
AdoptionRecord
      │
      ├── FollowUpRecord #1
      ├── FollowUpRecord #2
      └── FollowUpRecord #3
```

以下状态均保持不变：

```text
Animal.status = ADOPTED
AdoptionRecord 不修改
```

## 9. 异常事件流

| 编号 | 异常情况 | 系统处理 |
|---|---|---|
| E1 | 用户未登录或 JWT 失效 | 拒绝提交并要求重新登录 |
| E2 | 当前角色不是 `USER / RESCUER` | 后端拒绝提交 |
| E3 | 目标 `AdoptionRecord` 不存在或已删除 | 回滚事务并返回“领养记录不存在” |
| E4 | `AdoptionRecord.user_id != 当前用户.id` | 回滚事务并拒绝提交，不允许对他人的领养记录创建回访 |
| E5 | 回访字段格式或长度非法 | 拒绝提交 |
| E6 | 文字与健康情况去除首尾空白后均为空，且没有有效生活照片 | 拒绝提交；不创建 `FollowUpRecord` |
| E7 | token 重复，或任一临时文件不存在、不属于当前用户、已过期、已绑定其他业务，或图片格式、MIME、大小、数量不合法 | 拒绝提交；不得创建对应 `FollowUpImage`；不得删除未被本事务合法消费的文件 |
| E8 | 创建 `FollowUpRecord` 失败 | 整体回滚并执行文件补偿 |
| E9 | 创建任一 `FollowUpImage` 失败 | 整体回滚并执行文件补偿 |
| E10 | 正式文件复制失败 | 整体回滚，仅删除本事务已创建的正式副本，保留合法原临时文件 |
| E11 | 数据库事务提交失败 | 回滚数据库并仅清理本事务创建的正式副本 |
| E12 | 同一请求因重复点击或网络重试被再次执行 | 同一目标返回第一次结果；不同目标使用同一 key 时返回冲突，不重复创建记录或处理图片 |

## 10. OperationLog 处理

UC-07 不强制写入 `OperationLog`。

本用例没有审核或状态转换，只新增一条历史回访记录。以下字段已经能够满足“保存提交人和提交时间”的审计要求：

```text
FollowUpRecord.submitter_id
FollowUpRecord.created_at
```

因此 V1.0 不为普通回访提交重复写入关键状态操作日志。

## 11. 涉及功能需求

| 需求编号 | 与本用例的关系 |
|---|---|
| `FR-FOLLOW-01` | 已完成领养的 `USER / RESCUER` 可以针对本人领养记录提交回访 |
| `FR-FOLLOW-02` | 回访可以包含文字、健康情况和生活照片；三者至少包含一项有效内容 |
| `FR-FOLLOW-03` | 领养人只能操作属于本人的领养记录 |
| `FR-FOLLOW-06` | 保存提交人和提交时间 |
| `FR-FILE-01～07` | 回访图片上传、临时文件校验及文件一致性规则 |

以下是关联查看功能，不属于 UC-07 提交流程：

```text
FR-FOLLOW-04  ADMIN 查看全部回访
FR-FOLLOW-05  原负责 RESCUER 查看对应动物回访
```

## 12. 涉及业务规则

| 规则编号 | 内容 |
|---|---|
| `BR-12` | 用户只能操作属于本人且当前业务条件允许的数据 |
| `BR-22` | `RESCUER` 对领养和回访的只读查看权限通过原救助任务负责人确定 |
| `BR-24` | 角色变化不改变历史业务数据所有权 |

提交权限取决于 `AdoptionRecord.user_id`，原救助任务负责人关系仅用于判断 `RESCUER` 的只读查看权限。

## 13. 涉及实体与基数

主要实体：

```text
User
AdoptionRecord
FollowUpRecord
FollowUpImage
```

关系：

```text
AdoptionRecord 1 ─── 0..N FollowUpRecord
FollowUpRecord  1 ─── 0..N FollowUpImage
User            1 ─── 0..N FollowUpRecord
```

外键语义：

```text
FollowUpRecord.adoption_record_id → AdoptionRecord.id
必填，表示回访所属的领养记录

FollowUpRecord.submitter_id → User.id
必填，表示实际提交回访的领养人
```

## 14. 候选字段

### 14.1 FollowUpRecord

```text
id
adoption_record_id
submitter_id
content
health_condition
idempotency_key
created_at
```

`adoption_record_id` 与 `submitter_id` 必填；`content` 和 `health_condition` 可以分别为空，但 Service 层必须保证文字、健康情况和图片至少存在一项有效内容。

### 14.2 FollowUpImage

```text
id
follow_up_id
image_path
sort_order
created_at
```

其中：

```text
follow_up_id → FollowUpRecord.id
```

必填。`image_path` 仅保存服务器正式文件的相对访问路径，不保存本机绝对路径。
