# UC-02 审核救助线索

## 1. 基本信息

| 项目 | 内容 |
|---|---|
| 用例编号 | UC-02 |
| 用例名称 | 审核救助线索 |
| 主要参与者 | 系统管理员 `ADMIN` |
| 用例目标 | 管理员审核用户提交的待审核救助线索，并决定审核通过或驳回 |
| 触发条件 | `ADMIN` 在后台待审核线索列表中选择一条线索进行审核 |
| 前置条件 | 1. `ADMIN` 已登录且账号正常；2. 当前角色为 `ADMIN`；3. 目标 `RescueClue` 存在；4. 目标线索当前应处于 `PENDING_REVIEW` |
| 成功后置条件 | 审核通过时线索变为 `WAITING_ACCEPT`；审核驳回时线索变为 `REJECTED`；系统保存审核人、审核时间及必要的驳回原因，并写入操作日志 |
| 失败后置条件 | 本次审核请求不对 `RescueClue` 产生任何修改，不新增本次审核的操作日志；系统保留数据库中最新已提交的状态和审核信息，并向 `ADMIN` 返回最新业务状态 |
| 优先级 | Must |

冻结状态机明确规定：

```text
PENDING_REVIEW → WAITING_ACCEPT
PENDING_REVIEW → REJECTED
```

两种转换均由 `ADMIN` 执行；驳回必须填写原因。

## 2. 主事件流：审核通过

1. `ADMIN` 进入后台“救助线索审核”页面。
2. 系统展示当前待审核救助线索。
3. `ADMIN` 选择一条线索进入详情。
4. 系统展示地点、时间、动物描述、现场情况、联系方式、图片、发布人及当前状态。
5. `ADMIN` 核验线索内容。
6. `ADMIN` 选择“审核通过”。
7. 系统重新校验当前登录身份、`ADMIN` 权限和目标线索标识。
8. 系统开启数据库事务。
9. 系统执行带原状态条件的审核更新：

```sql
UPDATE rescue_clue
SET status = 'WAITING_ACCEPT',
    reviewer_id = ?,
    reviewed_at = NOW(),
    updated_at = NOW(),
    reject_reason = NULL
WHERE id = ?
  AND status = 'PENDING_REVIEW';
```

10. 系统检查受影响行数：

    - `affectedRows = 1`：审核状态更新成功，继续执行；
    - `affectedRows = 0`：回滚本次事务并重新查询目标线索：
      - 查询不到：转入 E3；
      - 查询得到但状态不再是 `PENDING_REVIEW`：转入 E4。

11. 系统写入 `operation_log`。
12. 系统提交数据库事务。
13. 系统提示 `ADMIN`“审核通过”。
14. 该线索进入 `WAITING_ACCEPT`，可供 `RESCUER` 后续接取。
15. 用例结束。

## 3. 备选事件流 A1：审核驳回

在主事件流第 6 步，`ADMIN` 判断线索不应通过审核：

1. `ADMIN` 选择“驳回”。
2. 系统要求输入驳回原因。
3. `ADMIN` 输入原因并提交。
4. 系统校验驳回原因不为空且不只包含空白字符。
5. 系统重新校验当前登录身份、`ADMIN` 权限和目标线索标识。
6. 系统开启数据库事务。
7. 系统执行带原状态条件的审核更新：

```sql
UPDATE rescue_clue
SET status = 'REJECTED',
    reviewer_id = ?,
    reviewed_at = NOW(),
    reject_reason = ?,
    updated_at = NOW()
WHERE id = ?
  AND status = 'PENDING_REVIEW';
```

8. 系统检查受影响行数：

    - `affectedRows = 1`：审核状态更新成功，继续执行；
    - `affectedRows = 0`：回滚本次事务并重新查询目标线索：
      - 查询不到：转入 E3；
      - 查询得到但状态不再是 `PENDING_REVIEW`：转入 E4。

9. 系统写入驳回操作日志。
10. 系统提交数据库事务。
11. 系统提示“线索已驳回”。
12. 发布人后续可以查看 `REJECTED` 状态及驳回原因。
13. 用例结束。

## 4. 异常事件流

| 编号 | 异常情况 | 系统处理 |
|---|---|---|
| E1 | `ADMIN` 未登录或 JWT 已失效 | 拒绝请求，要求重新登录 |
| E2 | 当前账号不是 `ADMIN` | 后端拒绝审核，不修改业务数据 |
| E3 | 目标线索不存在或已删除 | 返回“线索不存在或已删除”，本次审核失败 |
| E4 | 目标线索状态已不是 `PENDING_REVIEW` | 拒绝本次审核，返回数据库中的最新状态，不覆盖已经提交的合法业务结果 |
| E5 | 驳回原因为空或仅包含空白字符 | 拒绝驳回提交，提示填写有效驳回原因 |
| E6 | 更新 `RescueClue` 时发生数据库异常 | 回滚事务，本次审核失败 |
| E7 | 写入 `operation_log` 失败 | 回滚整个事务，避免出现“状态更新成功但日志缺失” |
| E8 | 提交事务失败 | 回滚本次事务，不产生半完成审核结果 |
| E9 | `ADMIN` 重复提交同一次审核请求 | 第一次成功后状态已不再是 `PENDING_REVIEW`；后续请求条件更新影响 0 行，按照 E3/E4 判定流程处理 |

冻结基线规定，未列出的状态转换均为非法，必须由 Service 层拒绝。

## 5. 事务与并发要求

审核通过必须原子完成：

```text
BEGIN
  ↓
条件更新 RescueClue
PENDING_REVIEW → WAITING_ACCEPT
  ↓
保存 reviewer_id / reviewed_at
  ↓
写入 OperationLog
  ↓
COMMIT
```

审核驳回同理：

```text
BEGIN
  ↓
条件更新 RescueClue
PENDING_REVIEW → REJECTED
  ↓
保存 reviewer_id / reviewed_at / reject_reason
  ↓
写入 OperationLog
  ↓
COMMIT
```

任何一步失败均执行 `ROLLBACK`。条件更新用于同时处理：

- 两个 `ADMIN` 并发审核；
- 发布人与 `ADMIN` 并发操作；
- 重复提交审核请求；
- 状态更新成功但审核日志写入失败。

## 6. 操作日志

### 6.1 审核通过

| 字段 | 值 |
|---|---|
| `business_type` | `RESCUE_CLUE` |
| `business_id` | 当前线索 ID |
| `operation_type` | `AUDIT_APPROVE` |
| `before_status` | `PENDING_REVIEW` |
| `after_status` | `WAITING_ACCEPT` |
| `operator_id` | 当前 `ADMIN` ID |
| `reason` | `null` |
| `created_at` | 当前时间 |

### 6.2 审核驳回

| 字段 | 值 |
|---|---|
| `business_type` | `RESCUE_CLUE` |
| `business_id` | 当前线索 ID |
| `operation_type` | `AUDIT_REJECT` |
| `before_status` | `PENDING_REVIEW` |
| `after_status` | `REJECTED` |
| `operator_id` | 当前 `ADMIN` ID |
| `reason` | 驳回原因 |
| `created_at` | 当前时间 |

`AUDIT_APPROVE / AUDIT_REJECT` 是 PetLink V1.0 已冻结的正式操作类型枚举名称；Service 必须校验其与 `RESCUE_CLUE` 的组合合法。

| 编号 | 内容 |
|---|---|

| `BR-16` | 审核通过后的线索发布人不得自行撤回 |

## 9. 涉及业务实体

| 实体 | 在 UC-02 中的作用 |
|---|---|
| `User` | 分别作为线索发布人和执行审核的 `ADMIN` |
| `RescueClue` | 保存线索内容、当前状态和审核信息 |
| `RescueClueImage` | 提供审核时需要查看的现场图片 |
| `OperationLog` | 保存审核状态变化的审计历史 |

`User` 与 `RescueClue` 之间存在两条不同语义的关系：

```text
RescueClue.publisher_id → User.id
必填，表示发布该线索的 USER / RESCUER

RescueClue.reviewer_id → User.id
审核前为空，审核成功后指向执行审核的 ADMIN
```

`RescueClue` 与 `OperationLog` 通过 `business_type + business_id` 建立逻辑关联，数据库设计阶段不一定设置直接外键。

## 10. RescueClue 审核相关候选字段

```text
id
publisher_id

location
found_time
animal_description
scene_description
contact

status

reviewer_id
reviewed_at
reject_reason

created_at
updated_at
```

- `publisher_id`：发布该线索的 `USER / RESCUER`；
- `reviewer_id`：执行审核的 `ADMIN`，审核前为空；
- `reviewed_at`：审核时间，审核前为空；
- `reject_reason`：仅审核驳回时必填，其他状态为空。

这些字段是当前用例推导出的候选字段，最终数据类型、长度、索引、外键和空值约束在数据字典阶段确定。

## 11. 状态影响

审核通过：

```text
PENDING_REVIEW
       ↓
WAITING_ACCEPT
```

审核驳回：

```text
PENDING_REVIEW
       ↓
REJECTED
```

只有审核通过路径会继续进入 UC-03：

```text
UC-01 发布救助线索
        ↓
PENDING_REVIEW
        ↓
UC-02 审核救助线索
        ↓
WAITING_ACCEPT
        ↓
UC-03 接取救助任务
```
