# UC-05 提交领养申请

## 1. 基本信息

| 项目 | 内容 |
|---|---|
| 用例编号 | UC-05 |
| 用例名称 | 提交领养申请 |
| 主要参与者 | 普通用户 `USER`、救助人员 `RESCUER` |
| 用例目标 | `USER` 或 `RESCUER` 对当前处于 `AVAILABLE` 状态的动物提交领养申请，形成待 `ADMIN` 审核的 `AdoptionApplication` |
| 触发条件 | `USER / RESCUER` 在目标动物详情页点击“申请领养”，进入申请表单 |
| 前置条件 | 1. 用户已登录且账号正常；2. 当前角色为 `USER` 或 `RESCUER`；3. 目标 `Animal` 存在；4. 目标动物当前应处于 `AVAILABLE`；5. 当前用户此前未对该动物提交过领养申请 |
| 成功后置条件 | 新增且仅新增一条状态为 `PENDING` 的 `AdoptionApplication`；申请人取自认证上下文；写入创建日志；`Animal` 状态保持 `AVAILABLE` |
| 失败后置条件 | 本次事务不提交新的 `AdoptionApplication`，不新增本次申请日志；`Animal` 及已有申请保持数据库中的最新已提交结果 |
| 优先级 | Must |

`USER` 和 `RESCUER` 都可以申请领养，包括 `RESCUER` 申请本人负责救助的动物；`ADMIN` 不作为申请人。申请成功不等于领养成功，也不会改变动物状态。

## 2. 用例边界

UC-05 负责：

```text
进入申请流程
→ 填写申请
→ 提交申请
→ 创建 AdoptionApplication(PENDING)
```

查看本人申请及状态、撤回申请和 UC-06 审核领养申请不属于 UC-05。

## 3. 主事件流

1. `USER / RESCUER` 在目标动物详情页点击“申请领养”。
2. 系统展示领养申请表单。
3. 申请人填写领养原因、居住情况、家庭成员情况、养宠经验和联系方式等信息。
4. 申请人确认信息并点击“提交申请”。
5. 前端进行必填项和基本格式校验，以改善用户交互。
6. 后端重新执行完整校验：

   - 当前登录身份有效；
   - 当前角色为 `USER` 或 `RESCUER`；
   - `user_id` 从认证上下文取得，客户端不得指定或覆盖；
   - `adoption_reason` 必填且长度合法；
   - `housing_condition` 必填且长度合法；
   - `family_members` 必填且格式合法；
   - `pet_experience` 必填且长度合法；
   - `contact` 必填且格式、长度合法；
   - 其他请求字段符合服务端业务约束。

7. 系统开启数据库事务。
8. 系统锁定并读取目标动物：

```sql
SELECT id, status
FROM animal
WHERE id = ?
FOR UPDATE;
```

9. 系统检查：

   - Animal 不存在或已删除：回滚并转入 E3；
   - `status != AVAILABLE`：回滚并转入 E4；
   - `status = AVAILABLE`：继续执行。

10. 系统创建 `AdoptionApplication`：

```text
user_id           = 当前认证用户 ID
animal_id         = 当前 Animal.id
adoption_reason   = 领养原因
housing_condition = 居住情况
family_members    = 家庭成员情况
pet_experience    = 养宠经验
contact           = 联系方式
status            = PENDING
created_at        = 当前时间
updated_at        = 当前时间
```

11. 数据库通过命名唯一约束最终保证同一用户不能重复申请同一动物：

```sql
CONSTRAINT uk_adoption_application_user_animal
UNIQUE (user_id, animal_id)
```

12. 插入成功后，系统写入申请创建对应的 `operation_log`。
13. 系统提交数据库事务。
14. 系统返回“领养申请提交成功，等待管理员审核”。
15. 用例结束。

## 4. 备选事件流

### A1：申请人取消提交

1. `USER / RESCUER` 在填写申请过程中选择“取消”或返回。
2. 系统终止当前填写流程。
3. 系统不启动创建 `AdoptionApplication` 的数据库事务。
4. 不创建 `AdoptionApplication`，不写入 `OperationLog`。
5. `Animal` 状态保持不变。
6. 用例结束。

## 5. 事务、加锁与并发要求

UC-05 的主事务为：

```text
BEGIN
  ↓
锁定 Animal
  ↓
确认 status = AVAILABLE
  ↓
INSERT AdoptionApplication(PENDING)
  ↓
UNIQUE(user_id, animal_id)
  ↓
写入 OperationLog
  ↓
COMMIT
```

### 5.1 为什么锁定 Animal

如果只读取状态后再插入申请，两步之间可能发生：

```text
AVAILABLE → SUSPENDED
```

或由 UC-06 产生：

```text
AVAILABLE → ADOPTED
```

因此必须在短事务内通过 `SELECT ... FOR UPDATE` 锁定 Animal、确认状态并创建申请。事务提交后 Animal 仍为 `AVAILABLE`，其他用户仍可提交各自的申请。

### 5.2 统一加锁顺序

凡一个写事务同时涉及 `Animal` 和 `AdoptionApplication`，统一采用：

```text
先锁定 Animal
→ 再读取、锁定或修改 AdoptionApplication
```

不得在其他 Service 中使用相反顺序。UC-06 必须沿用该规则，以降低多个领养写事务形成循环等待的概率。

### 5.3 重复申请

业务层可以提前查询已有申请以改善提示，但不能依赖“先查再插入”保证唯一性。数据库唯一约束是防止并发重复申请的最终保障。

无论历史申请状态为：

```text
APPROVED
REJECTED
WITHDRAWN
INVALIDATED
```

同一用户都不得再次申请同一动物。即使以后使用逻辑删除，删除记录仍占据 `(user_id, animal_id)` 组合；不得将 `deleted` 加入唯一约束以释放申请资格。

### 5.4 撤回申请事务

撤回只允许申请人操作属于本人的 `PENDING` 申请，并与审计日志处于同一事务：

```text
BEGIN
  ↓
条件更新 AdoptionApplication
PENDING → WITHDRAWN
  ↓
affectedRows = 1
  ↓
写入 WITHDRAW OperationLog
  ↓
COMMIT
```

`affectedRows = 0` 时查询最新记录，区分记录不存在、不属于本人或状态已经变化。日志写入或事务提交失败时整体回滚，不得出现申请已经撤回但审计日志缺失的结果。

## 6. 异常事件流

| 编号 | 异常情况 | 系统处理 |
|---|---|---|
| E1 | 用户未登录或 JWT 已失效 | 拒绝提交并要求重新登录 |
| E2 | 当前角色不是 `USER / RESCUER` | 后端拒绝请求；`ADMIN` 不允许提交领养申请 |
| E3 | 目标 Animal 不存在或已删除 | 回滚事务，返回“动物不存在或已下架” |
| E4 | Animal 当前状态不是 `AVAILABLE` | 回滚事务，返回最新动物状态，提示当前不可申请 |
| E5 | 申请必填字段缺失或格式、长度不合法 | 拒绝提交，不创建申请 |
| E6 | 插入申请时触发 `uk_adoption_application_user_animal` 唯一约束冲突 | 回滚当前事务；查询该用户针对该动物已有的申请，返回“已申请过该动物”及已有申请当前状态 |
| E7 | 创建 `AdoptionApplication` 时发生其他数据库异常 | 回滚本次事务，返回统一业务错误 |
| E8 | 写入 `operation_log` 失败 | 回滚整个事务，不形成“申请已创建但日志缺失”的结果 |
| E9 | 数据库事务提交失败 | 本次申请整体失败 |
| E10 | 用户重复点击提交 | 最多产生一条申请；后续重复请求由唯一约束拒绝并按照 E6 处理 |

业务层只能将指定命名唯一约束的冲突解释为重复申请。外键错误、非空约束错误或其他完整性异常不得伪装成“重复申请”。

## 7. 状态影响

UC-05 创建：

```text
不存在
  ↓
AdoptionApplication(PENDING)
```

Animal 保持：

```text
AVAILABLE
```

因此同一只 Animal 可以同时拥有多份来自不同申请人的 `PENDING` 申请。申请后续可能转换为：

```text
PENDING
├─ APPROVED
├─ REJECTED
├─ WITHDRAWN
└─ INVALIDATED
```

这些转换不属于 UC-05。

## 11. 涉及业务实体

| 实体 | 在 UC-05 中的作用 |
|---|---|
| `User` | 作为领养申请人 |
| `Animal` | 作为申请目标并承担可申请状态门控 |
| `AdoptionApplication` | 保存领养申请内容和初始状态 |
| `OperationLog` | 保存申请创建操作历史 |

关系为：

```text
User 1 ─── 0..N AdoptionApplication
Animal 1 ─── 0..N AdoptionApplication
```

每条申请必须满足：

```text
AdoptionApplication.user_id → User.id
AdoptionApplication.animal_id → Animal.id
```

二者均为必填关系。`OperationLog` 通过 `business_type + business_id` 与申请建立逻辑关联。

## 12. AdoptionApplication 当前确认字段

```text
id
user_id
animal_id
adoption_reason
housing_condition
family_members
pet_experience

status

```

初始状态为 `PENDING`。数据库唯一约束为：

```sql
CONSTRAINT uk_adoption_application_user_animal

```

`reviewer_id / reviewed_at / reject_reason` 由 UC-06 继续确认。

## 13. 前后业务衔接

```text
Animal = AVAILABLE
       ↓
UC-05 提交领养申请
       ↓
AdoptionApplication = PENDING
       ↓
UC-06 审核领养申请
```

若 UC-06 最终批准，将在一个事务中完成申请批准、领养记录创建、Animal 变为 `ADOPTED` 以及其他待审核申请失效。该流程不属于 UC-05。
