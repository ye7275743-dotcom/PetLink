# PetLink 计划书差距核查与下一轮改进方案

核查日期：2026-09-04。状态：方案待实施，不是新的全量验收通过报告。

## 1. 结论与核查范围

当前应描述为“核心业务链已有实现和历史自动化证据，产品入口、账户体验、统计呈现和兼容验收仍未完整”，不能把“72 个接口已对齐”直接等同于“整个应用已完成”。

依据：原始《PetLink-详细设计说明书-v1.0-Frozen(1)(1).docx》的第 1.3、2、5、9、10 章，当前 PetLink 源码，历史验收报告，以及服务器只读核查。历史候选目录不作为当前版本。

本轮读取计划书、前后端实现、线上构建文件和接口；在隔离内存环境复现登录缓存冲突。没有注册真实账号，没有启停、禁用、晋升或修改业务记录，没有修改业务代码或部署配置，也没有重新运行全部业务写入测试。浏览器页面读取超时，因此不声称本轮完成了线上页面逐项点击验收。

## 3. 计划内尚未完整交付的内容

### 3.1 PC 公共访问与注册入口

- 计划第 1.3 节允许 VISITOR 在 PC / 移动端查看 AVAILABLE 动物、已发布公告并注册；FR-AUTH-01、FR-ANIMAL-09、FR-NOTICE-01 与此相关。
- 现有 PC 唯一公开路由是 /login，其他路由是 ADMIN / RESCUER 工作台。没有 PC 公共动物/公告页面，也没有 PC 注册页面。
- Mobile 和公开接口已有相关能力，缺口在 PC 页面及跨端导流，不应误报为后端注册、动物浏览、公告模块完全没做。

证据：[PC 路由](/Users/a1/Desktop/软件课设/PetLink/petlink-pc/src/router/index.js:8)。

### 3.2 统计看板只接出了部分能力

- FR-STAT-01～04 要求各状态统计，RTM-M08-05 规定完整状态键；后端已经返回完整分布，PC 首页仅显示四个状态的指标卡，没有完整分布总览。

### 3.3 工作台的待办入口未充分落实

第 9.1 节要求把待处理业务放在第一视觉层。现在有待审计数，但指标不能直接进入对应队列，也没有实际待办摘要；同时占用了较大面积展示固定业务说明。应增加“待审核线索、待审核领养、待处置失败任务”的直达入口，救助人员突出“等待接取、待开始、进行中”。这属于交互交付不完整，不是主链后端缺失。

- 历史“40 项跨端 E2E”脚本主要经两个前端代理调用 API，不是完整浏览器按钮/表单操作测试；不能据此宣称所有 UI 已通过。

## 4. 本轮额外发现：同源登录缓存冲突（优先修复）

线上 PC 在 /，Mobile H5 在 /mobile/，两者同协议、IP 和端口，属于同一浏览器存储源。两个前端都使用 petlink_token 和 petlink_user。PC 直接 JSON 序列化用户；UniApp H5 对对象使用带 type/data 的包装，格式也不同。

使用当前两个 auth store 和 UniApp 的解析函数，在内存模拟共享 localStorage，结果：

1. PC 登录后，Mobile 初始化读取到 PC 的令牌，缓存角色解析为空。
2. Mobile 登录后，重新初始化 PC 读取到 Mobile 的令牌，缓存角色解析为空。
3. PC 退出会删除 Mobile 同名持久化令牌。

这是可复现的代码缺陷，在同一浏览器演示两端不同账号时尤其明显；不同设备没有共享这份 localStorage。尚未确认用户本次“看不到用户管理”的具体原因就是此缺陷。

改进：两端分别使用带 pc/mobile 命名空间的缓存键，处理旧键迁移，避免退出或切换账号影响另一端。共享的是同一个后台身份与业务数据库，不应共享不同前端正在使用的演示会话。角色变更仍以数据库当前角色为准，在页面进入/恢复、权限错误时重新拉取身份并更新导航。

证据：[PC 登录缓存](/Users/a1/Desktop/软件课设/PetLink/petlink-pc/src/store/auth.js:3)、[Mobile 登录缓存](/Users/a1/Desktop/软件课设/PetLink/petlink-mobile/src/store/auth.js:2)、[后端当前角色校验](/Users/a1/Desktop/软件课设/PetLink/server/src/main/java/com/petlink/security/JwtAuthenticationFilter.java:51)。

## 5. 建议实施顺序与验收标准

### 第一阶段：账户、注册和权限闭环

1. 先修同源登录缓存，确保 PC 管理员、手机网页版普通用户可在同一浏览器独立演示。
2. 完善管理员“用户管理”入口、账户/角色/状态筛选、注册时间、详情和业务计数。
3. 在已有 USER → RESCUER 基础上增加 RESCUER → USER。变更需二次确认、原因、操作人、时间和变更前后角色。
4. 有待开始/进行中任务时阻止直接降级，先完成任务或由管理员按已有异常处理流程处置。保留历史发布者、领养人和原救助负责人；降级后的档案维护需明确由管理员承接，不覆盖历史来源任务负责人。如以后增加人员交接，应独立设计当前责任关系及交接日志。
5. 不开放自行注册 ADMIN / RESCUER；默认仍只创建 USER。管理员任命属于独立敏感能力，本次不做无条件任意角色切换。
6. 增加 PC 公共注册入口，完善两端账号校验、确认密码、密码可见切换、重复账号提示、注册成功引导。均调用同一注册接口，后台刷新即可看到新用户。
7. 登录后按角色进入合适入口：普通用户进入已有公众服务端；救助人员/管理员进入工作台。不要让普通用户注册成功后立即撞上“无权进入电脑工作台”。普通用户完整桌面业务工作台并非原版范围，如要扩展需另记变更。

验收：注册 → 后台查到 → 晋升 → 救助入口出现 → 有活动任务降级被阻止 → 无活动任务降级 → 救助专属接口拒绝 → 历史本人数据仍保留；禁用后接口拒绝访问，恢复后正常；两端会话互不覆盖。以上均需真实页面和 API 两层验证。

### 第二阶段：公共首页、角色工作台和文案

- PC 公共首页：品牌介绍、可领养动物、已发布公告、简明参与流程、注册/登录、移动端入口；不登录可浏览公开内容。
- Mobile 首页：清晰的“我要领养 / 发布线索”主入口、动物卡片、公告和可阅读的参与指南；救助人员增加任务快捷入口。
- ADMIN 工作台：待办队列、完整统计、近期业务；RESCUER 工作台：待接取、本人任务、负责动物与回访。
- 不为填充首页而公开治疗中/已领养档案；如果加入成果统计，应提供权限安全的匿名聚合，不直接开放管理员统计 API，不硬编码虚假数字。
- 全面清除“第几模块”“永久幂等键”“事务”等开发说明；隐藏乐观锁版本和无必要的内部图片 ID；保留有业务价值的单号、状态、原因、图片限制和异常提示。版本等技术参数仍在内部正常传递。
- 非必要英文装饰统一中文；演示批次标签不再占据宠物名称等主要展示位置。涉及演示数据更名时应只处理明确标记的样例，不批量修改真实用户数据。

验收：首访无需猜入口；每个入口可到达实际功能；登录前后返回路径正确；没有装饰性的假按钮；界面文字面向使用者。

### 第三阶段：统计及整体验收

- 接出全部状态分布、日期范围、图例、真实值和正确零值；修正救助人员第一页计数问题。
- 建立覆盖同源部署的真实浏览器测试，补注册/用户管理/权限变化和跨端会话用例，并回归已有救助、领养、回访主链及异常分支。
- 复核 Chrome、Edge、HBuilderX；有真机条件时完成上传、权限、弱网、返回栈和安全区检查。
- 原 Frozen 设计保留，登记本次扩展（尤其角色降级），同步 API、规则、必要的数据库变更和 RTM；把“接口完成”“页面完成”“测试通过”“已部署”分列，避免再次以单一完成率代替交付情况。
- 先在本地开发/审查/测试，再备份线上数据库与上传文件、构建发布、部署后冒烟，保留回滚版本；不直接在服务器手工改源码，不影响 80 端口旧项目。

## 6. 不应混称为计划遗漏的项目

- 角色反向降级：本次新增；原版仅单向晋升。
- 管理员任命、修改/找回密码、验证码、操作日志查询页面：属于可考虑的账户增强，原版没有将这些页面列为必做。操作日志写入本身已有实现，不能说整个审计系统未做。
- HTTPS、独立强密码、备份恢复、依赖升级等：是面向公开运营的加固项；当前演示上线不等于正式生产验收。不要把这些全部冒称为原计划中不存在的具体 FR 条款。
- 商城、支付、即时聊天、医院预约、复杂推荐、自动回访任务：原计划第 1.2 节明确排除。
- 答辩 PPT、演示脚本、项目报告、完整彩排：按用户之前要求继续暂缓，不列入本轮开发。
