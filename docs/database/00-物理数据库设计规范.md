# PetLink V1.0 物理数据库设计规范

## 1. 数据库基线

```text
数据库：MySQL >= 8.0.16
存储引擎：InnoDB
默认字符集：utf8mb4
默认排序规则：utf8mb4_0900_ai_ci
```

MySQL 版本不得低于 8.0.16，以确保 `CHECK` 约束实际生效。

### 1.1 运行时区

建库脚本中的 `SET time_zone = '+08:00'` 只影响执行脚本的当前数据库连接。Spring Boot 运行时必须确保应用、JDBC 数据源连接和 MySQL 会话采用统一的系统约定时区（V1.0 为 `Asia/Shanghai / +08:00`），尤其是使用数据库 `NOW() / CURRENT_TIMESTAMP` 生成的时间字段。部署验收时应在应用连接中查询 `@@session.time_zone` 并核对。

## 2. 主键与外键

```text
所有业务主键：BIGINT UNSIGNED
所有对应外键：BIGINT UNSIGNED
```

外键列必须与被引用主键保持相同的数据类型及 `UNSIGNED` 属性。

## 3. 字符集与排序规则

| 字段类别 | 字符集与排序规则 | 语义 |
|---|---|---|
| 普通中文文本 | 继承 `utf8mb4_0900_ai_ci` | 支持中文描述、昵称、原因等内容 |
| 状态码、角色码 | `CHARACTER SET ascii COLLATE ascii_bin` | 大小写严格，与 Java 枚举保持一致 |
| 登录账号 | `CHARACTER SET ascii COLLATE ascii_general_ci` | ASCII 格式，登录与唯一性判断大小写不敏感 |
| 密码哈希 | `CHARACTER SET ascii COLLATE ascii_bin` | 原样保存 BCrypt ASCII 字符串 |

## 4. 命名规范

```text
表名、字段名：snake_case
主键：id
外键：{entity}_id 或具有明确业务语义的字段名
唯一约束：uk_{table}_{columns}
普通索引：idx_{table}_{columns}
检查约束：chk_{table}_{field}
```

领域实体 `User` 的物理表名为 `sys_user`，避免与 MySQL 的 `USER()` 和系统权限表混淆。

## 5. 认证与受控字段

以下字段不得信任客户端输入，必须从认证上下文或锁定后的数据库记录取得：

```text
当前操作人、发布人、申请人、提交人、审核人
业务关联产生的 user_id / animal_id 等冗余外键
```

角色授权由 Service 层执行；普通外键只能保证目标用户存在，不能保证其 `role_code` 满足业务要求。

## 6. 逻辑删除原则

不对所有表机械添加 `deleted`。只有业务明确允许删除且必须保留数据时才采用逻辑删除。产品化扩展中 `sys_user` 与 `announcement` 采用逻辑删除，以保留历史业务关联和审计链路。

## 7. 当前物理表范围

```text
15 张核心业务表
+ 1 张 temporary_file 技术支撑表
= 16 张基础物理表
```

技术支撑表不放入核心业务 ER 主图，但必须进入物理数据字典和最终建表脚本。

## 8. 状态与配套字段原子更新

当状态与时间、原因或审核信息存在组合 `CHECK` 时，状态及全部配套字段必须在同一条 `UPDATE` 中原子修改，并通过原状态条件及 `affectedRows` 判断转换是否成功。禁止先改状态、再用第二条 SQL 补写配套字段。

对于允许 `NULL` 的字段，`CHECK` 中的大小比较、字符串比较等表达式可能得到 `UNKNOWN`，而 MySQL 会接受结果为 `TRUE` 或 `UNKNOWN` 的行。因此，要求某状态下字段必填时必须显式写出 `IS NOT NULL`，不能只依赖 `> 0`、`>=` 或其他比较表达式间接排除 `NULL`。

长期由多个角色维护且可能发生并发覆盖的实体可增加 `version` 乐观锁。使用 MyBatis-Plus 自定义 SQL 时必须手工写入 `AND version = ?` 与 `version = version + 1`；所有档案和状态更新应保持统一版本语义。

## 9. 正式文件孤立清理

V1.0 不增加独立文件清理任务表。正式文件采用“数据库关联先提交、文件后删除”，删除失败时记录错误日志并由定时孤立文件扫描兜底。

扫描任务只处理最后修改时间早于 24 小时安全窗口的文件，并确认文件未被任一正式图片表引用、不存在有效 `temporary_file` 绑定流程，同时验证规范化真实路径仍位于配置的 `uploads` 根目录内。全部条件满足后才允许物理删除。

## 10. 审计日志只追加

`operation_log` 只允许新增和查询。Mapper 与 Service 不提供更新、删除能力；部署权限允许时，应用数据库账号对该表仅授予 `SELECT / INSERT`，不授予 `UPDATE / DELETE`。关键业务状态变化与必需日志必须位于同一事务。

## 11. 临时文件绑定与清理

`temporary_file` 使用 `UPLOADED / BOUND` 两状态，默认 TTL 由 `petlink.file.temporary-ttl=PT1H` 配置。多个 token 统一按临时文件 ID 升序加锁并使用条件更新一次性绑定。

绑定时保存服务端生成的 `formal_path`。数据库提交前采用临时文件复制，提交成功后删除原临时副本；事务失败只删除本事务创建的正式副本。清理 BOUND 行前必须通过 `business_type + business_id + formal_path` 精确确认正式图片关联与正式物理文件均存在。
